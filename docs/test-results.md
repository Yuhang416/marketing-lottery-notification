## 修复前（2026-10-28，基线 tag `before-upgrade` 之后的代码，业务逻辑未改）

### T1 重复开奖（P1）

命令：`./mvnw -o test -Prepro -Dtest=T1DuplicateDrawTest -Drounds=100`

做法：每轮新建一个活动、一个奖品（数量 1）、一个参与人，把同一份开奖参数连发两条，等状态稳定 6 秒后统计。

| 指标 | 结果 |
|---|---|
| 总轮数 | 100 |
| 正常（奖品 COMPLETED、1 条中奖记录、2 条通知任务） | **0** |
| 误撤销（有通知任务、没有中奖记录） | **100** |
| 重复（中奖记录或通知任务多于应有数量） | 0 |
| 有消息进入开奖死信队列的轮数 | 100 |
| 误撤销时通知已经发出（任务 DONE） | 1 |
| 误撤销时通知被取消（任务 CANCELLED） | 99 |

每轮最后的状态都一样：奖品 INIT、活动 RUNNING、中奖记录 0 条，但第一条消息写的 2 条通知任务还留在表里。

单独跑 1 轮并打开日志后，看到的过程是：
1. 第二条消息第一次处理时，写中奖记录撞上 `winning_record.uk_w_a_p_id`，于是进入补偿，补偿把第一条消息写的中奖记录删掉，并把状态改回初始状态。
2. 之后间隔 1 秒重试 4 次。每次校验都能通过（奖品已经被改回 INIT），但写通知任务时都撞上第一条留下的任务（`notification_outbox.uk_winner_channel`），又进入补偿。
3. 5 次都失败后，消息进入死信队列。

和计划里的预期对比：计划预期「出现误撤销」，实际是 100 轮全部误撤销，而且留下的通知任务会让这个奖品之后每次开奖都撞上同一个唯一键。最后这一点是根据重试过程推断的，没有单独测过「再开一次」。

### T2 开奖入口，消息路由不到（P3）

命令：`./mvnw -o test -Prepro -Dtest=T2UnroutableDrawTest -Drounds=3`

做法：删掉 `DirectExchange → DirectQueue` 的绑定后调用开奖，测完恢复绑定。

| 指标 | 结果 |
|---|---|
| 调用次数 | 3 |
| service 正常返回（接口会返回成功） | 3 |
| 被 Broker 退回的消息 | 3 |
| 进入开奖队列 / 死信队列 | 0 / 0 |
| 最终有中奖记录 | 0 |

接口返回成功，消息被退回后没人处理，丢失了。和预期一致。

### T3 双实例同时投递（P4）

命令：`TASKS=1000 scripts/repro-t3.sh`（跑了 3 次）

做法：写入 1000 条 PENDING 任务。两个 JVM 关掉消费者和自动扫描，约定在同一时刻各扫描一次，批大小 1000。最后读空通知队列，统计每个任务被投递了几次。

| 次数 | 两个实例开始扫描的时间差 | 收到的消息 | 重复投递 | 被投递 2 次的任务 |
|---|---|---|---|---|
| 第 1 次 | 0ms | 2000 | 1000 | 1000 |
| 第 2 次 | 3ms | 2000 | 1000 | 1000 |
| 第 3 次 | 1ms | 2000 | 1000 | 1000 |

两个实例的扫描完全重叠时，每个任务都被投递了 2 次。这个测试是故意让两边同时扫描的；正常运行时两边每 3 秒各扫一次，什么时候重叠取决于时机，这种情况没有测。

### T6 通知失败耗尽（P7）

| 指标 | 3 轮结果 |
|---|---|

### P2 两个事务之间进程退出

命令：`scripts/repro-p2.sh`（跑了 3 次）

做法：第一次运行时，事务一（状态流转）正常提交，在执行事务二 `saveWinnerRecords` 时直接 `Runtime.halt(1)`，不走异常和补偿；然后重新启动。

| 时间点 | 3 次结果都一样 |
|---|---|
| 进程退出后、重启前 | 奖品 COMPLETED、活动 COMPLETED、中奖记录 0、通知任务 0，开奖队列里有 1 条未处理的消息 |
| 重启后 | 消息被取走（队列剩余 0），奖品、活动仍是 COMPLETED，中奖记录 0、通知任务 0 |

开奖永久丢失：状态显示已经开过奖，但没有中奖记录，也没有通知。重启后消息为什么被直接确认：按代码看，是 `checkDrawPrizeParam` 发现奖品已完成后直接 return，这次没有打开日志确认。

## 修复后

环境和命令都和修复前一样。

### 步骤 2：开奖结算合成一个事务（2026-10-28）

改动：抢占奖品（`update ... where status = 'INIT'`）、状态流转、写中奖记录和通知任务合成一个事务；删掉逆向补偿；缓存改到事务提交之后写。T1、P2 加了验收断言。

**T1 重复开奖（P1）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 总轮数 | 100 | 100 |
| 正常 | 0 | **100** |
| 误撤销 | 100 | **0** |
| 重复 | 0 | 0 |
| 有消息进入开奖死信队列的轮数 | 100 | **0** |

修复后，第二条消息在第一步的条件更新就影响 0 行，日志打出「奖品已经开过，忽略本次开奖消息」后直接返回，不会写中奖记录，也不会撞唯一索引。断言通过。

**P2 开奖进行到一半时进程退出**

| 时间点 | 修复前（3 次） | 修复后（3 次） |
|---|---|---|
| 进程退出后、重启前 | 奖品 COMPLETED、活动 COMPLETED、中奖记录 0、通知任务 0 | 奖品 INIT、活动 RUNNING、中奖记录 0、通知任务 0（整个事务回滚了） |
| 重启后 | 中奖记录 0、通知任务 0，开奖永久丢失 | 奖品 COMPLETED、活动 COMPLETED、**中奖记录 1、通知任务 2** |

**回归**：`DrawPrizeTest`（单次开奖到通知发送的完整链路）通过。

### 步骤 3：开奖接口等 Broker 确认后再返回（2026-10-28）

改动：发送开奖消息时带上 `CorrelationData`，最多等 3 秒确认结果；只有 ack 并且没有被退回才返回成功，否则返回 `404 开奖消息发送失败，请重试`。T2 加了验收断言。

**T2 开奖消息路由不到（P3）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 调用次数 | 3 | 3 |
| 接口返回成功 | 3 | **0** |
| 接口返回失败（提示运营重试） | 0 | **3** |
| 消息进入开奖队列 | 0 | 0 |

消息仍然进不了队列（绑定被测试删掉了），区别在于接口如实告诉运营失败了，运营知道要重试。修复后的日志显示，路由失败时 Broker 返回的是 `ack=true`，同时把消息退回；所以只判断 ack 不够，还要检查消息有没有被退回。断言通过。

**RabbitMQ 整个停掉的情况**：没有测。要测得停掉本机的 RabbitMQ，没有做。

### 步骤 4：Outbox 多实例抢占、退避和重试上限（2026-10-28）

改动：投递器先在一个短事务里用 `select ... for update skip locked` 领取到期任务（`next_retry_time <= 当前时间`），同一事务里 `attempt_count + 1`，并按退避序列把 `next_retry_time` 往后推，当作租约；提交后再投递。投递失败只记录 `last_error`，等租约到期后重新领取。投递满 8 次的任务改成 `FAILED` 并打 ERROR 日志。正式配置的退避是 10、30、60、120、300 秒，抖动 ±20%。

时间统一由应用计算：应用按 JDBC 的 `serverTimezone=Asia/Shanghai` 写入时间，本机 MySQL 的 `now()` 用的是系统时区 PDT，两者差 15 小时，不能混用。

**T3 双实例同时投递（P4）**

| 次数 | 修复前：收到消息 / 重复 | 修复后：收到消息 / 重复 |
|---|---|---|
| 第 1 次 | 2000 / 1000 | 1000 / **0** |
| 第 2 次 | 2000 / 1000 | 1000 / **0** |
| 第 3 次 | 2000 / 1000 | 1000 / **0** |

修复后，两个实例开始扫描的时间差都在 3ms 以内，1000 条任务每条只投递 1 次，状态都是 PUBLISHED。断言通过。

**T4 永久失败的任务（P5）**

测试里把配置调小：上限 4 次、退避 3、6、12 秒、不加抖动，这样 60 秒内能跑完。

| 指标 | 修复前（60 秒） | 修复后（60 秒） |
|---|---|---|
| 每个任务的投递次数 | 20，还在继续 | **4，然后停止** |
| 每次间隔 | 固定 3.0 秒 | 3.1、6.1、12.1 秒（逐次变长） |
| 最终状态 | PENDING | **FAILED** |
| `attempt_count` | 0 | 4 |
| `last_error` | null | 投递 4 次仍未成功，最后一次错误：消息被退回：NO_ROUTE |
| ERROR 告警日志 | 无 | 5 个任务各 1 条 |

断言通过。

**T7 实例领取任务后宕机**

命令：`TASKS=20 scripts/repro-t7.sh`

做法：进程 A 领取 20 条任务（租约已写入并提交）后，在发出第一条消息前 `halt(1)`；进程 B 正常运行投递器（每 3 秒扫描一次），然后读空通知队列统计。

| 时间点 | 结果 |
|---|---|
| A 退出时 | 20 条都是 PENDING，`attempt_count=1`，租约约 9 秒后到期 |
| B 启动时 | 仍然是 20 条 PENDING；B 启动用了 16 秒，租约已经过期 |
| B 启动后 0.5 秒 | 20 条全部被领取并投递，每条只投递 1 次，重复 0 条，状态 PUBLISHED，`attempt_count=2` |

断言通过。这次 B 启动时租约已经过期，所以只验证了「租约到期后任务会被别的实例接手」，没有验证「租约到期前别的实例不会领走」。后者由 T3 覆盖：两个实例同时领取，没有重复。

**回归**：`DrawPrizeTest`、T1（3 轮）、T5（3 轮）、T6（1 轮）都通过。T5、T6 的通知链路经过新的领取逻辑，行为和之前一致：T5 仍然每轮发送 2 次，T6 仍然停在 PUBLISHED。这两个问题在步骤 5 修复。
